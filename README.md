# GR5293 Final Project: RAG-Based Course Assistant

This project builds an end-to-end Retrieval-Augmented Generation (RAG) assistant for a Generative AI course.  
The system answers course-related questions using lecture slides as its document base, rather than relying only on the language model's prior knowledge.

## Project Goal

The goal is to evaluate whether a course-specific RAG system can produce answers that are more **grounded in course materials** than a plain LLM baseline.

### Core comparison
- **Baseline:** the generation model answers the question directly without retrieval.
- **RAG system:** relevant lecture chunks are retrieved first, and the model answers using only those retrieved chunks.

## Final System Overview

The final system has five stages:

1. **Document ingestion**
   - Lecture PDFs are stored in `data/raw/`
   - PDFs are parsed with PyMuPDF
   - If native extraction fails on a page, OCR fallback is applied with Tesseract

2. **Preprocessing**
   - Extracted pages are saved in structured JSON
   - Pages are lightly cleaned
   - Pages are chunked into retrieval-ready units

3. **Retrieval**
   - Chunks are embedded with `sentence-transformers/all-MiniLM-L6-v2`
   - Embeddings are indexed with FAISS
   - Top-k chunks are retrieved for each user query

4. **Generation**
   - Retrieved chunks are inserted into a grounded prompt
   - The answer is generated by the current API backend using only the retrieved material

5. **Evaluation**
   - Questions are run through both the baseline and the RAG system
   - Outputs are saved for comparison
   - Manual scoring focuses on correctness, groundedness, and retrieval relevance
   - A small top-k ablation study is included

## Generation Backend Migration

The project initially used the **Google Gemini free tier** for answer generation.  
During repeated evaluation runs and demo development, the free-tier API frequently encountered:
- rate limits,
- temporary availability issues,
- and instability for batch evaluation.

To improve stability while keeping the retrieval pipeline unchanged, the generation backend was later migrated to **AGICTO's OpenAI-compatible API**.

This means:
- the extraction pipeline is unchanged,
- chunking and FAISS retrieval are unchanged,
- only the final answer-generation backend was replaced.

Legacy Gemini-based scripts are retained in `src/archive/` for reference.

## API Key Setup

The current default generation backend uses **AGICTO's OpenAI-compatible API**.

Set your API key in the same terminal session before running the generation scripts:

```bash
export AGICTO_API_KEY="your_api_key_here"
```

Verify it with:

```bash
echo $AGICTO_API_KEY
```

## Reproducibility Note

The retrieval pipeline is reproducible locally without an API key:
- PDF extraction
- OCR fallback
- chunking
- embeddings
- FAISS retrieval

The final answer-generation stage requires an API key for the configured provider.  
In the current version, the active baseline, RAG, evaluation, and demo scripts use AGICTO.

If an AGICTO key is not available, the user can still:
- run retrieval-only inspection with `python src/test_retrieval.py`
- inspect saved evaluation outputs in `eval/`
- review the archived Gemini scripts in `src/archive/`

## How to Run the Pipeline

### Step 1: Extract PDFs

```bash
python src/extract_pdf.py
```

This:
- reads PDFs from `data/raw/`
- uses native text extraction first
- falls back to OCR for low-text pages
- saves page-level JSON and TXT outputs

### Step 2: Chunk the extracted pages

```bash
python src/chunk_text.py
```

This produces `data/processed/all_chunks.json`.

### Step 3: Build the retrieval index

```bash
python src/build_index.py
```

This creates:
- `data/index/faiss.index`
- `data/index/chunk_metadata.json`

### Step 4: Test retrieval

```bash
python src/test_retrieval.py
```

Use this to inspect whether the retriever returns relevant chunks for sample course questions.

### Step 5: Run the baseline

```bash
python src/baseline_agicto.py
```

This asks the current generation backend the question directly, without retrieval.

### Step 6: Run the RAG assistant

```bash
python src/rag_qa_agicto.py
```

This:
- retrieves top-k chunks from FAISS,
- builds a grounded prompt,
- generates an answer using only the retrieved material,
- and prints the retrieved sources.

### Step 7: Run evaluation

```bash
python src/evaluate_systems.py
```

This script compares:
- baseline answers
- RAG answers

It also:
- saves partial progress,
- resumes from completed questions,
- and supports the current API backend.

### Step 8: Run the top-k ablation study

```bash
python src/ablation_topk.py
```

This compares answer behavior across different retrieval depths (for example, `k=2`, `k=4`, and `k=6`).

### Step 9: Run the Streamlit demo

```bash
streamlit run app/streamlit_app.py
```

## Current Findings

The main findings of the final version are:

- The baseline model is often broadly correct on definition-style questions.
- The RAG system produces answers that are more explicitly grounded in course materials when retrieval succeeds.
- The main bottleneck is **retrieval quality**, not answer generation quality.
- Failure cases typically occur when the retriever misses the best lecture chunk.
- In the top-k ablation, `k=4` gives the best overall balance, while larger retrieval depth can help difficult cases like LoRA but may introduce more noise.

## Limitations

Current limitations include:
- OCR noise on image-heavy or diagram-heavy slides
- retrieval misses for some concepts if the most explanatory chunk is not surfaced
- dependence on an external API for answer generation
- evaluation still uses a relatively small course-specific question set

## Future Work

Potential future improvements include:
- improving retrieval for known failure cases such as LoRA
- trying hybrid retrieval or reranking
- adding confidence estimation for weak retrieval cases
- expanding the evaluation set
- improving deployment and packaging for broader reuse

## Notes

- Raw lecture PDFs may be course-restricted and should be handled carefully.
- Large generated artifacts under `data/processed/` and `data/index/` are typically not intended for public version control unless needed for reproducibility.
- The final project is designed first as a reproducible course prototype, then as a polished demo system.
